# Local SQLite database output

This directory holds `jellite.sqlite`, generated locally by running the sync script (see
`sync/` and `infra/setup-gcp.md`). The file itself is regenerated by `.m3u` playlists in
your library and baked into the backend's container image at deploy time (see
`infra/deploy.sh`).

## Committed via Git LFS

`data/jellite.sqlite` **is committed to git** (a deliberate choice, so `infra/deploy.sh`
can deploy directly from a checkout without re-running a full sync first), but since it's
a large binary file that changes on every sync run, it's tracked via **Git LFS** (see
`.gitattributes`) rather than as a plain blob — this keeps `git clone`/`fetch` fast by only
downloading the LFS content for the version actually checked out, instead of every
historical version accumulating in `.git` on every clone. Make sure `git lfs` is installed
(`brew install git-lfs && git lfs install`) before cloning/pulling this repo, or the file
will check out as a small text pointer instead of the real database.

`data/jellite.sqlite-wal` and `data/jellite.sqlite-shm` are **not** committed (see
`.gitignore`) — they're ephemeral SQLite WAL-mode sidecar files, regenerated automatically
whenever the DB is opened (both backend and sync use `journal_mode=WAL`), and hold no data
that isn't already checkpointed into `jellite.sqlite` itself. The sync script automatically
runs `PRAGMA wal_checkpoint(TRUNCATE)` before it exits, so `jellite.sqlite` is always ready
to commit/deploy immediately after a sync run without a manual step.
